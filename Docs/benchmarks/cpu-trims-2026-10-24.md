# Firmware emulation CPU trims — 2026-10-24

YouKnow 1.3.5 takes repeated bookkeeping out of the emulated A-5 assigner CPU and the B-2 serial-trace CPU without changing a rendered sample. The baseline is `000e9e0` (1.3.4). This is an unreleased source change measured on a development container; no installed plug-in or Rack Extension was replaced and nothing here is a Reason-host measurement.

## Where the time went

A callgrind profile of the Rack product configuration (below) put about 12 % of the engine's instructions in the original-firmware path: the A-5 foreground executed instruction by instruction (`FirmwareAssignerScheduler::advanceTo`), its UART, and the B-2 serial trace. Unlike the filter and chorus arithmetic, this is integer emulation, so it can be made cheaper with no question of rounding. Two costs stood out, both paid once per emulated instruction (about 950 A-5 instructions per 64-frame block): the scheduler staged every instruction in a copy of its 176-byte execution state and copied it back on success, and both emulators cleared their pending-instruction record with an aggregate `= {}`. GCC lowers both to `rep movsb` / `rep stos` string operations.

## Changes

One mechanism per commit, each verified bit-identical before the next.

1. **In-place completion** (`FirmwareAssignerScheduler::advanceTo`). The instruction executes directly on the caller's execution state. A snapshot taken first is restored on every failure path (an execution error, a full event ledger, a refused UART write), so a failed completion still leaves the last committed frontier exactly as before; bus RAM stays in the bounded write ledger until every check has passed, as it did. One block copy per instruction instead of two.
2. **Field-wise pending clear** (A-5 scheduler and B-2 serial trace). `clearPending()` assigns the same zero values member by member instead of the aggregate `pending = {}`, which GCC 13 compiled to a byte-wise `rep stos`.
3. **Snapshot only what can fail.** A skipped instruction, or one whose `execute()` case touches only registers, flags, interrupt state and the input pins (`cannotFail()`: no bus read or write, no stack, no peripheral write, no event except a jump's single ForegroundPass marker), cannot fail once one event slot is free, so it no longer takes the snapshot. That is 72 % of the instructions in this workload. Every operation not on the list, including any added later, keeps the snapshot. The snapshot is held in a local union so nothing is initialized unless it is taken; `<optional>` was avoided because no Rack-compiled source in the portfolio uses it.

Firmware programs, instruction semantics, timing, event order, the UART and every DSP path are unchanged.

## Audio parity

The 2026-10-23 null-test harness ([`nulltest.cpp`](cpu-trims-2026-10-23/nulltest.cpp)) renders every factory and product preset through the product configuration — `ActiveProductFidelityProfile`, measured converter chart, PolyZoned/Cubic/RK4Single, Aging 50 %, six voices, 1x, Original timing, 64-frame callbacks — for one 3.6 s phrase after the demo renderer's 0.37 s pre-roll, and writes raw stereo float32. Each candidate's files were compared with the baseline's byte for byte (`cmp`), which is stricter than a residual.

- 48 kHz, Normal Circuit Rate: **all 144 presets byte-identical** after each of the three commits ([table](cpu-trims-2026-10-24-null-test.csv)).
- 48 kHz, Max Circuit Rate: the first thirteen presets (A11–A25) byte-identical after commit 3.
- Benchmark stream hashes (FNV-1a over every output sample, 300 callbacks after warm-up) equal the baseline's at every commit for four presets (A11, A61, B31, YB3) and the synthetic resonant patch at 48 kHz Normal, 44.1 and 96 kHz Normal, 48 kHz Max (two presets) and Direct timing at 2x and 4x.

Determinism holds by construction: the changes touch integer emulator bookkeeping only.

## Thread CPU

All runs interleave baseline and candidate, alternating which runs first each repetition, on a four-core container that other builds were loading throughout (load average about 18). `CLOCK_THREAD_CPUTIME_ID` around each call; the reduction is the median of the per-repetition ratios.

**The firmware path alone** ([`fwbench.cpp`](cpu-trims-2026-10-24/fwbench.cpp): the A-5 foreground through `FirmwareAssignerAudioBridge`, one 64-frame block of CPU states per call, from the scheduler regression's warm fixture, with a note on and off every 256 blocks; 4000 blocks per run, 15 paired runs, Rack-like flags). The B-2 serial trace is not in this benchmark.

| Step | Before µs/block | After µs/block | Paired reduction | Runs favouring |
| --- | ---: | ---: | ---: | ---: |
| 1. In-place completion | 33.24 | 23.69 | 28.0 % | 15/15 |
| 2. Field-wise pending clear | 24.06 | 21.96 | 6.7 % | 15/15 |
| 3. Snapshot only what can fail | 21.84 | 16.96 | 22.2 % | 15/15 |
| baseline → 1.3.5 | 35.26 | 18.17 | 47.6 % | 15/15 |

**The whole engine**, per step (the 2026-10-23 `bench`, 48 kHz Normal, A11 Brass Set 1, 1000 measured callbacks, 30 paired runs): commit 1 1.37 % (24/30 favouring), commit 2 0.01 % (15/30), commit 3 0.36 % (20/30). The firmware path is about 5 % of a block, so the smaller two steps (about 0.3 % and 0.7 % expected from the component timings) sit at or below this machine's run-to-run resolution on the whole engine; the component benchmark is what resolves them. ## Considered and not shipped

- **Persistent scratch for the bridge's discarded scheduler events.** `FirmwareAssignerAudioBridge::advanceTo` zero-fills a fresh 1024-entry (24 KiB) event ledger for every source slice, about three per block, only to read its count. Keeping it in the bridge state saves 0.8 % of instructions, but the firmware benchmark moved by 2.0–2.4 % with only 9–13 of 15 runs favouring, nothing measurable on the whole engine, and it would add 24 KiB to the persistent state. Not shipped.
- **Three more square roots in line** (`outputSummerClip`, `closedLoopSpectralFactor`, the bucket-noise normalization). Bit-identical and 0.29 % fewer instructions, but the clip itself, the busiest of the three, got about 0.35 ns faster per call at roughly 460 calls per block: about 0.02 % of a block. Not shipped.
- **Compile-time orders in the covariance transition series** (`cascadeCovariance`), turning the divisions by one, two and four into folds and exact multiplies. Bit-identical, but a microbenchmark of the function measured no change (about 330 ns per call either way) and instructions rose 0.3 %. Not shipped.
- **Arithmetic changes in the filter, chorus and cutoff law** remain out for the reason recorded on 2026-10-23: the fifteen self-oscillating presets diverge from any last-bit change.
- **Next candidate, not attempted:** `OtaCascade::process` spends about as many instructions on per-interval setup (sanitizing the trajectory, planning the tableau, per-node arrays) as on the right-hand-side evaluations of the common full-interval RK4 rung.

## Tests

The DSP test tree (`-DYOUKNOW_BUILD_PLUGIN=OFF -DBUILD_TESTING=ON`, Release, GCC 13, x86-64), on the final tree:

- `unit` tier: 122 of 122 tests passed.
- `fuzz` tier: `YouKnow.DspFuzz` passed.
- `YouKnowDSPCxx17` (the Rack's C++17 embedded build) builds, and its embedded test executables are in the `unit` tier above.
- Per commit: the 144-preset null test byte-identical, the benchmark hashes equal, and the scheduler, audio-bridge and serial-trace suites passing (for commit 1 also the assigner-audio and scheduler-audio suites), built directly against that commit's firmware sources.
- The `audio` tier (about two hours here) was not run: these commits change no DSP arithmetic, and every preset's rendered samples are byte-identical. The `render` tier (the editor screenshot) belongs to the plug-in build and was not run.

## Reproduce

```sh
# harnesses: Docs/benchmarks/cpu-trims-2026-10-23/ (engine) and cpu-trims-2026-10-24/ (firmware)
H=Docs/benchmarks/cpu-trims-2026-10-23; F=Docs/benchmarks/cpu-trims-2026-10-24
$H/build.sh /path/to/baseline-checkout bench /tmp/bench-baseline rack
$H/build.sh . bench /tmp/bench-candidate rack
valgrind --tool=callgrind --collect-atstart=no /tmp/bench-candidate original 48000 normal 300 2 1 0
$H/build.sh /path/to/baseline-checkout nulltest /tmp/nulltest-baseline plugin
$H/build.sh . nulltest /tmp/nulltest-candidate plugin
/tmp/nulltest-baseline /tmp/null-base original 48000 normal
/tmp/nulltest-candidate /tmp/null-cand original 48000 normal
for f in /tmp/null-base/*.f32; do cmp "$f" "/tmp/null-cand/$(basename "$f")"; done
$H/paired_timing.sh /tmp/bench-baseline /tmp/bench-candidate /tmp/timing.csv 10 1000
$F/step_timing.sh engine /tmp/bench-baseline /tmp/bench-candidate 1 30 >> /tmp/steps.csv
# fwbench: build line at the head of fwbench.cpp, once per checkout
$F/step_timing.sh firmware /tmp/fwbench-baseline /tmp/fwbench-candidate 1 15 >> /tmp/steps.csv
```
